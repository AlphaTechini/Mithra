## Goal
The backend can run a distribution cycle end to end on the ledger: take the record-date snapshot, compute pro-rata amounts in code, run every deterministic check with actual values, write the memo through a pluggable memo writer, propose through `Mandate_Propose` (which writes the decision record), and then either count down with a Hold button and execute within the Mandate, or wait for approvals and execute once the threshold is met. Payments go out as real token-standard transfers inside `Mandate_AgentExecute`; preapproved holders are paid in one step, others get a pending transfer that is reconciled when they accept. The UI never sees "Paid" before the ledger confirms. Sealing a Mandate goes through BitSafe governance on LocalNet. All of it is reachable through the REST routes in the shared contract.

## Requirements (verbatim from specs.md)
| ID | Requirement | Acceptance |
|---|---|---|
| L1 | The agent can execute a distribution only through the Mandate, and only if the total is at or under the Mandate cap. | Script: total = cap succeeds; total = cap + 0.0000000001 fails. |
| L2 | Every payee in an agent-executed distribution held fund units on the record date, and each amount equals the pro-rata share computed from the record-date snapshot (with a documented rounding rule). | Script: adding a non-holder fails; altering one amount fails. |
| L3 | At most one distribution per cycle per organization. | Script: second execution for the same cycle fails. |
| L4 | A proposal that needs approval cannot execute below the organization's threshold, and executes once the threshold is met. | Script: 1 of 2 fails; 2 of 2 succeeds. |
| L10 | Every agent-executed or agent-proposed distribution produces a decision record containing: trigger, input fingerprints (hashes), checks with results, memo, verdict, approvals, and payment references. | Script: execution without a decision record is impossible by construction. |
| A3 | MUST compute amounts in code (not in the LLM). | Unit test: proposal amounts equal the pure function's output; LLM output is never used as an amount. |
| A4 | MUST run all deterministic checks listed in `details.md` Section 7 on every proposal, with actual values shown. | Unit tests per check. |
| P1 | Payments MUST be real CC transfers using the Canton token standard (CIP-56) interfaces, so USDCx can be added later without redesign. | Code review: no CC-specific shortcuts outside an asset adapter. |
| P2 | Holders with auto-receive (preapproval) MUST be paid in one step; holders without it MUST receive a pending transfer and the UI MUST show it as awaiting acceptance. | Both cases demonstrated. |
| P4 | The UI MUST NOT show "Paid" until the ledger confirms the transfer. | Test with a slow or failed submission. |
| P5 | Before executing, the system MUST check the treasury balance covers the total plus an estimated fee buffer; if not, block with "Add funds". | Test with low balance. |
| U6 | The auto-execute path shows a short countdown with a "Hold" button before submitting. | Demo. |
| L6 | Changing the Mandate (cap, threshold, schedule, asset) requires a new treasurer signature. The agent cannot modify it. | Script: agent-submitted change fails. |
| N8 (governance part) | … a governed action (Mandate change) cannot execute below its confirmation threshold and succeeds once met. | Recorded test results in the repo. |

Deterministic checks (details.md section 7), all run on every proposal: total exceeds the auto-execute cap; treasury balance insufficient for total plus fees; a payee did not hold units on the record date; a distribution already exists for this cycle; total deviates from the trailing average of previous cycles by more than the policy threshold; a holder's units changed sharply in the days before the record date; the amount was set by a prompt that differs from the policy's fixed amount (if the policy has one).

## Design you must follow
Files (all under `apps/backend/src/`):
- `cycle/prorata.ts` — `computeProRata(total: string, holdings: { holder: string; units: number }[]): Payout[]`, the exact rule in `docs/ledger-model.md` ("Pro-rata rule", including step 5 rejections) with `decimal.js` (`ROUND_DOWN`, 10 places), and `unitsAt(recordDate, changes)`. Test against **every** case in `daml/test-vectors/prorata.json` (read the file in the test; map labels to fake party ids that sort in the same order — check how the Daml test sorted them, by `partyToText`).
- `cycle/period.ts` — cycle ids are the distributed month `YYYY-MM`; label `September 2026`; default cycle for "Run cycle now" = the previous calendar month in UTC; record date by rule: `last_day_of_previous_month` (relative to the payment date = the last day of the cycle month) and `day_before_payment`; `nextRun(cron, tz, from)` with `croner`.
- `cycle/checks.ts` — one pure function per check returning `CheckResult` (`code` exactly: `cap`, `balance`, `non_holder`, `duplicate_cycle`, `deviation`, `unit_spike`, `prompt_amount`) with `actual` and `limit` strings showing real values in the vocabulary of `userflow.md` section 9 (e.g. `Total 1,200 CC vs 3-cycle average 410 CC, +193%`; `Holder C: 600 → 1,500 units (+150%) in the 30 days before Sep 30`). Rules: `cap` blocking; `non_holder` blocking; `duplicate_cycle` blocking and, if failed, the engine refuses to propose with the message `A distribution for September 2026 has already been executed`; `deviation` blocking (passes with "No earlier cycles to compare" when there is no history; trailing average over the last `trailingCycles` executed cycles); `unit_spike` blocking (a holder who went from 0 to positive inside the window counts as a spike); `prompt_amount` blocking (passes as "Not applicable" when the policy has no fixed amount or the trigger is not a prompt); `balance` **non-blocking for the verdict** (an empty treasury should not send a cycle to approvers) but the engine never executes while the live balance is below `total + feeBuffer`: status `needs-funds` with `fundsShortfall` (P5). Record this decision in a comment and in your report. Amount formatting in check text: thousands separators, trailing zeros trimmed, asset symbol.
- `cycle/fingerprint.ts` — canonical JSON (sorted keys, no whitespace) → SHA-256 hex. Input fingerprints on every proposal: `register` (the record-date holdings), `mandate` (terms + version), `history` (previous totals used for deviation), `balance`, `payouts`, and `prompt` when the trigger is a prompt (A12 for the prompt text; model request/response fingerprints come from the memo writer).
- `cycle/memo.ts` — `interface MemoWriter { write(input: MemoInput): Promise<MemoResult> }` where `MemoInput` has the cycle, payouts with display names, checks, history and holder changes, and `MemoResult = { memo: string; memoSource: 'ai' | 'template' | 'ai-unavailable'; advisoryChecks: CheckResult[]; modelFingerprints: Fingerprint[] }`. Implement `TemplateMemoWriter` (deterministic, plain English, names failed checks). The AI writer is M5; it plugs into the same interface. **The engine must enforce A5 itself**: drop any advisory check whose `source` is not `ai` or whose `blocking` is true, and never let a memo writer change deterministic checks.
- `cycle/engine.ts` — `createCycleService(deps)` returning `CycleService` with:
  - `run({ trigger: 'schedule' | 'prompt' | 'manual', triggerDetail, cycleId?, total?, recordDate?, promptText?, modelFingerprints?, actorParty })` (`modelFingerprints`: fingerprints of the agent conversation turn that asked for the cycle, A12; merged with the memo writer's into the decision record) → `{ cycleId }`. Starts asynchronously after reserving the cycle in `cycle_runs` (the unique key is the double-run guard; a conflict returns the existing cycle id, not an error, unless that run failed, in which case it can start a new attempt). Steps, each published as a `timeline` event and stored in `agent_events` (`kind: 'timeline'`, payload = `TimelineStep`): `woke` "Woke up" (detail: trigger), `snapshot` "Snapshot taken" ("4 holders on Sep 30"), `amounts` "Amounts computed" ("1,200 CC split by units"), `checks` "Checks run" ("6 passed, 1 flagged"), `review` "Review written", `verdict` ("Within mandate" or "Needs 2 of 3 approvals"), then `execute` when it runs. Total defaults to the policy's fixed amount; if there is none and no total was given, fail with `Say how much to distribute, for example "Distribute 1,200 CC for September."`.
