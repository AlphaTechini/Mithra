## Goal
With `NETWORK=mainnet`, the same product runs on Canton MainNet with Grofty Wallet: people connect Grofty and sign in by signing a challenge (verified on the server), and every action that a person signs — creating the treasury charter and organization, sealing the Mandate, issuing and accepting units, approving and rejecting, cancelling, granting/denying/revoking audit access, filing and withdrawing audit requests, accepting a pending payment, and the treasurer's payout — is prepared by the server as ledger commands, signed and submitted in the browser with `prepareExecuteAndWait()`, then confirmed back to the server, which continues the flow. Holders are guided to turn on auto-receive in Grofty. Payments link to the MainNet explorer. Grofty's specifics are handled: single-party submission, 3-minute approval expiry (`-32603`), user rejection (`4001`), signed out (`4100`), missing extension, Grofty older than 2.0.4.

**Backend signing layer (`apps/backend/src/signing/`)**:
- `Signer` interface: `submit(intent: Intent): Promise<SignResult>` where `Intent = { kind: string; actor: string; commands: Command[]; disclosedContracts?: DisclosedContract[]; description: string; followUp: FollowUp }`. LocalNet implementation: submits through `LedgerClient` (actAs the actor, readAs treasury where the current code does) and runs the follow-up immediately (current behavior; all existing tests must stay green). MainNet implementation: stores the intent in a new `wallet_intents` table (Drizzle migration: id, party, kind, commands jsonb, disclosed jsonb, command_id, description, follow_up jsonb, state `prepared|submitted|completed|failed|expired`, update_id, error, created_at, expires_at = +10 min) and throws `WalletSignatureRequired(prepared)` → HTTP `409` `{ error: { code: 'sign_in_wallet', message: 'Approve this in Grofty Wallet.', prepared: { intentId, commandId, commands, disclosedContracts, description, party } } }`.
- `POST /api/wallet/intents/:intentId/complete { updateId }` (the intent's own party only): verifies the transaction on the operator's participant (`updateById` with the parties the operator node hosts that are stakeholders, e.g. the agent) when visible — at minimum that the update exists and its `commandId` matches; marks completed; runs the follow-up (e.g. record `tx_refs`, activity entries, advance the seal, mark the cycle executed, reconcile payments); returns `{ intent: { id, state }, next?: <the resource the UI should refetch> }`. `POST /api/wallet/intents/:intentId/fail { code, message }` records a failure (rejected, expired) so the UI and the activity log can say so.
- Refactor every person-signed write to go through the `Signer`: treasury routes (charter create on MainNet — new `POST /api/org/charter` for MainNet only, where the treasurer creates `TreasuryCharter` with treasury = treasurer = their party and agent/operator from env —, `POST /api/org`, `POST /api/holders/issue`, holder accept units, holder accept payment), cycle routes (approve, reject, cancel), the seal (`governance/mainnet.ts`: `Org_SealDirect`; state `awaiting-signature` until the intent completes, then `sealed`), the payout (`TreasurerPayoutExecutor`: `Mandate_TreasuryExecute` with legs from the asset adapter; the treasury's input holdings come from the browser — see below — so the payout intent is prepared by `POST /api/cycles/:cycleId/payout/prepare { holdings: [{ contractId, templateId, createdEventBlob, synchronizerId }] }` (treasurer): the server validates the holdings by decoding nothing it cannot verify — it passes them as disclosed contracts and lets the ledger check them — and computes the live balance from the Grofty holdings list for P5; cycle status `awaiting-signature` while waiting), audit routes (request create/withdraw by the auditor; grant/deny/revoke by the treasurer). The agent and operator writes stay server-side on both networks.
- Session (`apps/backend/src/routes/session.ts` and `src/auth/`): `POST /api/session/mainnet/challenge` → `{ nonce, message }` (message: `Sign in to Mithra\nParty: <party>\nNonce: <nonce>\nIssued: <ISO time>`; the party is in the request body `{ partyId }`; store the nonce for 5 minutes, single use); `POST /api/session/mainnet/sign-in { partyId, publicKey, signature, nonce }` → checks the namespace of `partyId` equals the fingerprint of `publicKey` (computed as above with Node `crypto`), verifies the Ed25519 signature (`tweetnacl` or Node `crypto.verify` with an Ed25519 key) over the message's UTF-8 bytes, then creates the session for that party; errors: `401 invalid_signature` "Grofty's signature did not match this party.
