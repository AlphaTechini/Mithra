## Verified facts to build on
LocalNet (Splice 0.6.12 bundle, `https://github.com/digital-asset/decentralized-canton-sync/releases/download/v0.6.12/0.6.12_splice-node.tar.gz`, extracts to `splice-node/`; compose files in `splice-node/docker-compose/localnet`):
```bash
export LOCALNET_DIR=<cache>/splice-node/docker-compose/localnet IMAGE_TAG=0.6.12
docker compose --env-file $LOCALNET_DIR/compose.env --env-file $LOCALNET_DIR/env/common.env \
  -f $LOCALNET_DIR/compose.yaml -f $LOCALNET_DIR/resource-constraints.yaml \
  --profile sv --profile app-provider --profile app-user up -d --wait
# down: same with `down -v`
# console: same files, `run --rm console` (profile console); see the console entrypoint below
```
- One `canton` container runs all three participants; one `splice` container runs the validators. Docker network name: `${DOCKER_NETWORK:-localnet}`. Inside the network the canton container is reachable as `canton`.
- Ports (host and in-network): app-provider ledger gRPC 3901, admin 3902, JSON 3975; app-user 2901, 2902, 2975; sv 4901, 4902, 4975; validator admin 3903/2903/4903; UIs 3000 (app-provider), 2000 (app-user), 4000 (sv, scan at `scan.localhost:4000`).
- Auth: HS256 JWT, secret `unsafe`, `{"aud":"https://canton.network.global","sub":"ledger-api-user"}`; `ledger-api-user` is admin on every participant.
- Token standard registry for CC (app-provider validator): `http://localhost:3000/api/validator/v0/scan-proxy` (app-user equivalent on 2000; from the wallet SDK's LocalNet constants). DSO party: `GET http://localhost:3000/api/validator/v0/scan-proxy/dso-party-id` — **unverified path**; if you cannot confirm it from the bundle (`splice-node/docs/html` contains the Scan/validator OpenAPI pages; grep them), document how to read the DSO party id and mark it for verification.
- Console container entrypoint (bundle `docker/console/entrypoint.sh`): generates JWTs with `jwt-cli`, then runs `/app/bin/canton ${CONSOLE_OP} --no-tty -c /app/app.conf ${CONSOLE_SCRIPT}` where `CONSOLE_OP=run` and `CONSOLE_SCRIPT` is set only when `MULTI_SYNC=true`. Participants are remote participants named `app-provider`, `app-user`, `sv` in `/app/app.conf` (Scala identifiers need backticks: `` `app-user` ``). To run your own script, add a compose override that mounts your `.sc` file and an entrypoint wrapper that mirrors the original (generate the three tokens, source `/app/pre-startup/on/*.sh`, then `canton run --no-tty -c /app/app.conf /mithra/<script>.sc`).

DecMan (BitSafe), image `public.ecr.aws/dlc-link/decentralization-manager:v1.13.0` (distroless, `ENTRYPOINT ["dec-party-manager","serve"]`, data under `$DECPM_DIR/data`):
- Env per instance: `DECPM_DIR=/app`, `DECPM_HOST=0.0.0.0`, `DECPM_PORT` (HTTP), `DECPM_NOISE_PORT`, `DECPM_PUBLIC_ADDRESS` (the container name, reachable by the other instances), `DECPM_CANTON_ADMIN_HOST=canton`, `DECPM_CANTON_ADMIN_PORT` (3902/2902/4902), `DECPM_CANTON_LEDGER_HOST=canton`, `DECPM_CANTON_LEDGER_PORT` (3901/2901/4901, gRPC), `DECPM_CANTON_SYNCHRONIZER=global`, `DECPM_CANTON_NETWORK=devnet`, `DECPM_INSECURE=true` (LocalNet unsafe auth; mints HS256 `unsafe` tokens with sub `ledger-api-user`), `DECPM_TOPOLOGY_PROPAGATION_DELAY_SECS=3`, `DECPM_PEER_WAIT_POLL_DELAY_MS=500`, `DECPM_LOG_FORMAT=text`. Join the LocalNet docker network (external). Map HTTP 8081/8082/8083 to the host. Mount `localnet/.data/dm-{a,b,c}` at `/app/data`.
- Mapping: DM A → app-provider (3901/3902), DM B → app-user (2901/2902), DM C → sv (4901/4902). Noise 9001/9002/9003.
- Bring-up sequence (from DecMan's own e2e, `integration-tests/common.sh` and `crates/decman/tests/common/phases/*.rs`):
  1. Wait for `GET /node-config` and a non-empty `GET /keys/status` `.public_key` on each instance.
  2. Participant ids: `GET /node-config` → `.node.participant_id`.
  3. On every instance `POST /network-config` with the JSON array of all three peers `[{ "participant_id", "name", "address": "<container name>", "port": <noise port>, "public_key", "party": null }]`, then **restart the three instances** (peer keys load at startup) and wait again.
  4. Create the party: on DM A `POST /onboarding {"party_id_prefix":"mithra-treasury","peer_ids":[<B participant id>,<C participant id>],"threshold":2}`; on B and C poll `GET /invitations` for `.invitations[] | select(.invitation_type=="Onboarding")` and `POST /invitations/accept {"id": <id>}`; poll `GET /onboarding/status` on A until `.status` is `completed` (fail on `failed`). The party appears in `GET /decentralized-parties` (`.parties[].party_id` — inspect the shape; it may be an object with `prefix`).
  5. Member parties: on each node's JSON API `POST /v2/parties {"partyIdHint":"mithra-member-<a|b|c>","identityProviderId":""}`, then `POST /v2/users/ledger-api-user/rights` granting `CanActAs` and `CanReadAs` for it; on each DM `PUT /party-config {"dec_party_id","member_party_id","user_id":"ledger-api-user","packages":{"governance_action":"#governance-action-v1","governance_core":"#governance-core-v1"}}` (keycloak fields omitted in insecure mode — verify on the owner's machine; if DecMan rejects it, document the error).
  6. DARs: on DM A `POST /dars/distribute {"dar_files":[{"filename","data":<base64>}...],"peer_ids":[B,C]}` with governance-action, governance-core and `mithra-v1-0.1.0.dar`; accept `Dars` invitations on B and C; poll `GET /dars/distribute/status`. (If the governance DARs are already vetted, DecMan should still succeed; check `GET /packages/vetted`.)
  7. GovernanceRules: on DM A `POST /contracts {"decentralized_party_id","participant_ids":[A,B,C],"participant_parties":[mA,mB,mC],"operator_party":<operator>,"contracts":[{"id":"mithra-governance-rules","name":"GovernanceRules","package_id":"#governance-core-v1","module_name":"Governance.Rules","entity_name":"GovernanceRules","fields":[{"type":"decentralized_party"},{"type":"party_set","parties":[mA,mB,mC]},{"type":"int64","value":2},{"type":"rel_time","microseconds":1800000000},{"type":"none"}]}]}`; accept `Contracts` invitations on B and C; poll `GET /contracts/status`; then `GET /governance/state?party_id=<dec party>` gives the rules contract id.
  8. Operator as additional proposer: on two nodes `POST /governance/confirm {"party_id","rules_contract_id","action":{"type":"governance_add_additional_proposer","additional_proposer":<operator>},"governance_type":"core_self"}`, then on one node `POST /governance/execute` with the same body plus `"confirmation_cids":[...]` (from `GET /governance/confirmations?party_id=...`; inspect the response shape and pick the confirmations for this action).
  9. Charter (Mithra governed action): as the operator on node A's JSON API, create `#mithra-v1:Mithra.Governance:CharterProposal {governanceParty: <dec party>, proposer: <operator>, treasurer, agent, operator}`; on DM A and DM B `POST /governance/confirm {"party_id","rules_contract_id","action":{"type":"generic_vote","description":"x"},"governance_type":"core_domain","proposal_cid":<cid>}`; then `POST /governance/execute {..., "confirmation_cids":[..], "disclosed_contracts":[], "governance_type":"core_domain", "proposal_cid"}`. Afterwards a `TreasuryCharter` is visible to the treasurer on node A.
- Mithra parties, all on node A (app-provider) so that taking node B offline in the BitSafe demo does not affect payees: `mithra-operator`, `mithra-agent`, `treasurer`, `approver-1`, `approver-2`, `approver-3`, `holder-a`, `holder-b`, `holder-c`, `holder-d`, `auditor`. Grant `ledger-api-user` on node A `CanActAs` for all of them and `CanReadAs` for the treasury dec party.
- Node names and operators (configurable in `localnet/nodes.env`, defaults): A "Node A", operator "Mithra Labs (app provider)"; B "Node B", operator "Ledgerline Fund Services (fund administrator)"; C "Node C", operator "Canton super validator (synchronizer operator)". Hosting threshold 2 of 3.
